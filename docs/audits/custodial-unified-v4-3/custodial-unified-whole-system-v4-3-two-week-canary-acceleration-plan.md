# Memphis Zoo Custodial Program — V4.3 Two-Week One-Phone Canary Acceleration Plan

**Objective:** One controlled Moto G canary in fourteen implementation days after Day-0 architecture/design authorization; all pre-Day-1 closure is outside that clock  
**Scope:** Canary, not fleet release  
**Priority:** Memphis Zoo Custodial Program  
**Method:** Parallel isolated worktrees, frozen contracts, one serialized integration authority, token-efficient model routing

---

## 1. Hard truth

The program cannot safely reach a canary by merely polishing the existing employee shell. The current source still carries duplicate authority and old product paths.

The fastest safe route is:

```text
bounded architecture closure
→ independently checked design contracts
→ parallel foundation implementation
→ migration/rollback rehearsal
→ admitted APK
→ bound physical acceptance
→ one-phone canary
```

The objective is aggressive but remains plausible for a **single controlled canary** because substantial mechanisms already exist:

- native credential vault and enrollment/removal foundation;
- device identity and assignment epochs;
- atomic completion intent and idempotency foundations;
- Messenger identity/outbox and tests;
- Events parser/API and tests;
- notification assignment checks and durable jobs;
- clean rebuild, schema fingerprints and recovery tooling;
- APK signer, versionCode, DEX/manifest and producer/consumer admission.

These are retained behind corrected authority contracts rather than rewritten gratuitously.

---

## 2. What the fourteen-day target means

Success at Day 14 means:

- one admitted release tuple;
- one designated Moto G 2025;
- one enrolled test employee/device identity;
- one bounded set of real or clearly labeled test locations/tags;
- core employee Home/Schedule/Messages/Events/Feedback flow;
- ambient NFC into Start Cleaning;
- restroom and exhibit completion;
- protected offline work and exactly-once reconciliation;
- manager visibility and recovery;
- critical notifications with exact physical behavior;
- tested rollback/restore readiness;
- one controlled canary period with evidence review.

It does **not** mean:

- fleet rollout;
- every optional guest/AI/Moxie feature;
- broad personnel analytics;
- every future operations-platform module;
- Build 22 retirement.

---

## 3. Acceleration rules

1. Custodial work outranks Athanor/platform expansion.
2. No full-repository rediscovery by every model.
3. Mechanical work goes to Spark; cross-domain decisions go to premium reasoning.
4. Each mission consumes frozen input contracts and emits one evidence artifact.
5. One worktree, one owner, one bounded objective.
6. Shared registries, migration order and release tuple have one serialized owner.
7. No two branches independently invent record, authority, principal or occurrence semantics.
8. No patch preserves an unregistered legacy authority.
9. Passing tests are not proof unless they exercise the admitted path.
10. Every day ends with an evidence gate, not a percentage estimate.

## 6. Pre-Day-1 architecture closure sprint

Target duration: **24–48 focused hours** using parallel Codex worktrees.

### Track A — Control artifacts

- package/stage-state schema;
- object registry;
- complete joined CAP trace and reverse registry;
- record registry;
- principal/service-principal/grant/tool registry;
- authority-set dependency/compatibility/transition registries;
- gate-to-design-impact matrix.

### Track B — Authority inventory

- source writer/reader graph;
- database function/trigger/cron/grant graph;
- backend route/worker/tool graph;
- frontend/native direct-write and old-route graph;
- retirement manifest.

### Track C — State models and fixtures

- offline original-actor/reassignment;
- occurrence concurrency/correction/next cycle;
- location split/merge/in-flight work;
- notification provider crash/duplicate/stale-visible behavior;
- Messenger visibility/hold/restore;
- Event revision/impact/reversal;
- rollback/restore interruption.

### Track D — Operational decision packet

Research-backed choices are prepared for Eric in compact tables. Questions are limited to genuine policy, not engineering mechanics.

### Track E — Physical preparation

- exact Moto G/Fully Kiosk/tag inventory;
- test location and employee identities;
- required audio and accessibility fixtures;
- rollback device state;
- day-by-day physical script.

### Pre-Day-1 gate

Advance only when:

- replan audit finds no BLOCKER;
- standalone v4.3 has been written and internally audited;
- targeted independent architecture audit finds no unresolved blocker;
- structure-changing Day-1 decisions are recorded;
- schema/component design is explicitly authorized.

If this gate slips, the canary date slips. It is not hidden inside implementation.

## 7. Fourteen-day execution

### Day 1 — Freeze contracts and design

Evidence gate:

- accepted v4.3 exact commit;
- approved decision ledger;
- package/object/CAP/record/principal/authority-set registries frozen;
- isolated schema and component design complete;
- targeted design audit reports no blocker;
- branch ownership and generated contract fixtures published.

### Day 2 — Clean schema and authority foundation

Evidence gate:

- disposable clean rebuild succeeds;
- prior-schema upgrade fixture exists;
- record/authority/principal tables and constraints conform to registries;
- RLS/grants/search paths/service principals have negative tests;
- no application runtime owns generic migration SQL.

### Day 3 — Occurrence, ownership and writer fencing

Evidence gate:

- ownership compiler/publication transactions defined and tested;
- occurrence command/state/concurrency fixtures pass;
- current writers/resolvers are inventoried;
- unregistered writer admission test is red then green;
- static candidate workbook remains blocked.

### Day 4 — Session, completion and original-actor offline path

Evidence gate:

- session start captures exact actor/device/epoch/authority/location/occurrence;
- completion transaction is atomic;
- employee A offline → phone reassigned to B → reconnect can never attribute to B;
- conflict/quarantine and manager recovery work.

### Day 5 — Manager product and recovery

Evidence gate:

- exact ownership/current cleaner/actual cleaner/status/readiness projections;
- work request versus transfer commands separated;
- phone reassignment and lost-phone recovery;
- Read Only field/route/asset negative tests;
- `OPEN` manager action path uses approved policy.

### Day 6 — Native employee shell and protected store

Evidence gate:

- Employee Home contains only title/name/Schedule/Messages/Events/Feedback;
- prohibited modules/assets/routes absent from employee build graph;
- protected session/draft/queue store passes restart and upgrade tests;
- Karen-safe error vocabulary enforced.

### Day 7 — Ambient NFC and completion UX

Evidence gate:

- native NFC routing from all app states;
- normal valid tag reaches Start Cleaning without Scanner/name selection;
- constrained failure recovery exists without normal QR/Scanner product;
- restroom and exhibit normal paths require no more than three primary decisions.

### Day 8 — Messenger, Events, Feedback and contractor

Evidence gate:

- Messenger stable send/outbox and zero-stale-recipient fixtures;
- hide/delete/reappearance/hold semantics conform;
- Event import/save/read cannot write schedule;
- Event approval/cancel/reversal works;
- Feedback attachments obey local/security/retention rules;
- contractor failure states and secure-link behavior conform to approved policy.

### Day 9 — Notifications and GPS

Evidence gate:

- occurrence-rooted child intents and presentation groups;
- final recipient/credential/epoch/authority validation;
- provider-crash reconciliation and duplicate-tolerant device presentation;
- already-visible stale cancellation;
- active-session-only GPS negative tests;
- exact audio and non-audio fixtures ready for phone.

### Day 10 — Full integration and shadow comparison

Evidence gate:

- clean-source full test suite passes;
- cross-domain replay and correction fixtures pass;
- old client/new backend and new client/old backend are admitted or rejected deterministically;
- read paths create no authority;
- shadow comparison classifies every difference;
- no legacy writer survives unexplained.

### Day 11 — Migration and rollback rehearsal (not final release proof)

Evidence gate:

- clean rebuild and upgrade rehearsal;
- legacy drain/fence/deny proof;
- candidate self-contained restore bundle rehearsal verifies;
- database/object restoration does not activate partially;
- interruption/retry and rollback rehearsal passes;
- pending local work treatment is proved.

### Day 12 — Release admission

Evidence gate:

- clean-source signed APK;
- package, versionCode, certificate/public key, DEX, manifest, vault and asset graph verified;
- frontend/backend/schema/config/provider/Fully Kiosk tuple recorded;
- producer and independent consumer admission pass;
- rollback package and physical script frozen.

### Day 13 — Bound physical matrix and one-phone canary start

Evidence gate:

- Moto G/Fully Kiosk containment;
- NFC from lock and every app state;
- screen off, process death, reboot and offline queue;
- restroom/exhibit completion;
- reassignment conflict;
- exact audio, non-audio equivalent, grouping and stale replacement;
- Messenger privacy/performance;
- GPS session boundary;
- Karen no-rescue common path;
- controlled canary starts only after all pass.

### Day 14 — Canary evidence review

Evidence gate:

- exact canary tuple archived;
- accepted work evidence and manager inspection verified;
- no duplicate/cross-employee/stale-recipient/legacy-writer defect;
- rollback drill readiness confirmed;
- every defect classified by root cause and gate;
- decision made whether to continue canary, correct and repeat, or begin fleet-release evidence.

Fleet rollout is not automatic.

- physical-test preparation;

Parallel branches:

- schema/backend;
- native employee;

- verification/release.

Serialized items:

- migration sequence;
- generated contracts;
- shared record/principal/authority-set registries;

## 10. Token controls

- Hash every input and output.
- Reuse unchanged research and reasoning.
- Do not rerun complete whole-system audits when only one artifact changed.
- Use targeted re-audits tied to changed artifact IDs.
- Keep premium sessions fresh and bounded.
- Stop each session after its named deliverable.
- Use mechanical scripts before premium review.
- Reserve Sol for cross-domain acceptance, migration/security and release decisions.
- Use Spark for inventories, lint, tests, evidence and bounded code.

---

## 11. Schedule risks and countermeasures

| Risk | Countermeasure |
|---|---|
| Policy decisions delayed | Compact decision packet with recommended defaults and structural impact |
| Whole-system rereading burns tokens/time | Frozen registries, evidence cache and bounded missions |
| Shared files conflict | One serialized control-plane/migration owner |
| Legacy authority survives | Machine-generated complete graph and fail-on-unregistered admission |
| Native physical defect appears late | Physical scripts and exact device/tag preparation before Day 1 |
| Offline identity corruption | Original-actor fixture required before any canary path |
| MCP security change breaks ChatGPT connection | Staged read/write plane separation with tested rollback; no toggle-and-pray production change |
| Fourteen-day goal becomes excuse for patches | Daily evidence gates and root-cause disposition |
