Custodial physical tag identity candidate

This candidate is based on frontend 8979c72d0d4fe98ff46e2d3831bf897165f6cf37 (Build56). It requires a new reviewed/admitted frontend APK; it is not present in the installed Build56. No new backend field, proof signature version, activation shortcut, tag rewrite or location configuration is introduced.

Android supplies Tag.getId() and Tag.getTechList() at discovery, without additional RF communication. The earlier isolated candidate's NTAG213/215/216 GET_VERSION allowlist was a design choice, not an owner or Android requirement. It is removed. Both actual live NDEF paths now use the complete observed ID plus its RF technology; NDEF content, location equality or browser input cannot substitute for the original ID.

Supported observations are standards-compliant NFC-A fixed IDs of 4, 7 or 10 bytes and ISO15693/NFC-V fixed 8-byte UIDs. NFC-A is not restricted by manufacturer, chip model, NDEF Type 2 or MIFARE variant; IsoDep/MIFARE/Ndef secondary technologies do not change its RF namespace. NFC-V retains all bytes in Android's observed order. Empty/all-zero/all-FF IDs, malformed lengths, ambiguous RF families and known NFC-A random IDs (4-byte first byte 08), fixed non-unique IDs (4-byte first byte xF), cascade markers and reserved F8 are refused. Technology-list order is irrelevant. No GET_VERSION query, product probe or extra RF connection delays Start.

This is an ordinary observed-ID equality check. It assumes standards-compliant tags whose IDs are fixed and distinct across the actual installed inventory. It is not cryptographic proof of chip authenticity or resistance to duplicated IDs. Some historical NFC-A 4-byte IDs were reused and cannot be identified as such from one discovery; those inventory collisions are an explicit limitation. Known random IDs are rejected, but metadata cannot establish every arbitrary/emulated device's stability. NFC-B, NFC-F and NFC Barcode are conservatively unclassified in this candidate: Android's generic getId contract alone does not give a reliable fixed-versus-changing discriminator for every such product. Their refusal is a bounded support policy, not a statement that all tags of those technologies are unstable or require replacement. An existing fixed-ID product can be added with its actual identifier evidence; there is no purchase/setup requirement. No location fallback is permitted.

Primary documentation retrieved September 30, 2026: [Android Tag.getId/getTechList](https://developer.android.com/reference/android/nfc/Tag#getId()) documents discovery metadata and stable/random/absent IDs; [NXP AN10927](https://www.nxp.com/docs/en/application-note/AN10927.pdf), sections 2.1–2.3, documents NFC-A UID sizes, random/non-unique/reused IDs; [NXP NTAG213/215/216 data sheet](https://www.nxp.com/docs/en/data-sheet/NTAG213_215_216.pdf), section 8.5.1, documents nominal manufacture-fixed UID; [Android NfcV](https://developer.android.com/reference/android/nfc/tech/NfcV) identifies ISO15693; [ST25DV data sheet](https://www.st.com/resource/en/datasheet/st25dv04k.pdf), section 8, documents its standards-compliant read-only 64-bit UID. Protocol-based support for NFC-A and NFC-V is an implementation inference under the stated fixed/distinct inventory assumption. Android NFC-F emulation also permits configurable NFCID2 ([Android NfcFCardEmulation](https://developer.android.com/reference/android/nfc/cardemulation/NfcFCardEmulation)); it is not evidence of fixed-ID behavior of an arbitrary Zoo NFC-F tag. The Athanor router previously could not initialize its cache/database outside this worker's write permissions; responsible-authority sources were fetched directly as fallback. No source document is copied into the review packet.

ReaderCallback and external live Tag paths read NDEF, observe the supported hardware identity, and persist the URL plus identity in the encrypted native handoff. The opaque URL handoff carries no identity. The native scan-entry journal copies the identity without exposing it to the WebView. Start preserves it on the protected occurrence with original session/device/location/start entry and monotonic time. Finish compares identity before binding/mutating the finish entry and before capturing completion time. A different observed ID at the same canonical location is refused. GPS is not involved in this path.

The first independent review of candidate77563522 returned SOURCE HOLD for blocking NFC operations in Activity callbacks and stale Finish-handle recovery. The correction queues both external live-Tag dispatch and ReaderCallback on one Activity-owned executor. Intent normalization returns a neutral startup immediately; load cannot process the original cold Tag twice. The worker performs live NDEF I/O before deriving identity from the same Tag, then posts delivery to the UI. Android [Ndef.connect](https://developer.android.com/reference/android/nfc/tech/Ndef#connect()) and [getNdefMessage](https://developer.android.com/reference/android/nfc/tech/Ndef#getNdefMessage()) prohibit blocking calls from the main thread. A source-bound Java executor regression uses synthetic RF adapters and tests prompt normalization while reads are blocked, same-Tag binding, serial reads, no duplicate cold attempt, failed-read refusal and executor shutdown. It is not a physical NFC test.

The second review of candidate28fc1890 returned SOURCE HOLD for persisting a handoff before a queued UI lifecycle guard could decline its delivery, losing its only locator. The isolated correction places the lifecycle guard, encrypted handoff persistence, Activity Intent locator retention and navigation together on the UI thread. Lifecycle callbacks on that thread cannot run between persistence and locator retention. Finishing/destroyed Activities create no new handoff; executor shutdown remains best effort, with correctness supplied by the delivery guard. NFC radio calls stay on the worker and GPS is not consulted. A definitive persistence refusal leaves the original Intent; a downstream navigation exception still leaves the new locator. The small encrypted commit now runs on the UI thread; actual storage latency, Android lifecycle/recreation, process death, KeyStore and RF interruptions require device acceptance. The controlled lifecycle regression extracts the actual enqueue/dispatch methods, uses a real Java worker, and reproduces both after-read and before-UI invalidation, repeated capacity exhaustion, successful recovery, and queued lifecycle callbacks. It does not prove process-death recovery or a physical scan. R3 accepted this successful-write ordering; its remaining failure-state finding follows.

The third review of candidate5c65ccbc accepted the successful-write lifecycle ordering but held F-1R3: a failed SharedPreferences commit can already have changed memory, so returning an empty locator silently consumes pending capacity. The next isolated correction distinguishes durable success, verified rollback and uncertainty. A bounded retry commits the identical ciphertext and requires successful commit plus exact readback. Failure restores the exact prior ciphertext or absence; an empty result is allowed only after verified rollback or before any write. If neither outcome can be confirmed, the native result retains the candidate ID and the Activity saves its Intent locator without navigation. A process-wide guard shared by store instances refuses handoff claims and additional reads until the exact prior bytes are durably restored. It never clears the namespace, rewrites occurrence/timer/drafts/proof data, weakens enrollment/identity checks or treats memory visibility as durability. Unknown third bytes remain untouched and require recovery. The guard is process-local; actual process-death/Android disk behavior and Intent retention remain runtime gates, not a promised disk transaction. Focused actual native/store and generated Activity fixtures cover failed-memory writes, repeated failure then healthy read, original-byte preservation, uncertainty refusal, locator retention and missing-identity refusal. Changed-input independent review remains pending.

The existing device binding, enrollment, snapshot admission, monotonic clock/boot continuity, authenticated Start/Finish proofs, completed receipt matching and queue/server cleanup remain authoritative. Existing proof signatures bind native entry IDs; the new equality check runs before completion proof issuance. No server-side independent hardware authentication is claimed.

Recovery preserves the original identity and timer. The prior isolated `ntag21x.v1:` observation format remains valid and compares only to the identical bytes in the NFC-A namespace; stored protected identities are never normalized or rewritten. It does not match another UID, another RF family or an identityless historical Start. The browser retains the exact Finish handle before capture; native capture validates identity before binding it. A definitive identity refusal releases only that rejected browser Finish attempt, retaining the cleaning and drafts. If a fresh read is already available after interruption, it is tried once; uncertain persistence refusals keep the saved handle. A Finish already captured in the durable journal retries only with its exact saved finish entry, without requiring a new live tag after transport interruption. A failure between saving end time and saving its finish proof retains the original end and identity; a same-observation retry completes the journal. This does not invent a new completion or claim server acceptance.

Historical 11/12-field occurrences and identityless handoffs/entries remain readable. Already captured legacy finishes retain exact delivery/reconciliation. Legacy unfinished work cannot acquire an invented original identity or finish under the new guarantee; it remains saved and blocks new work as before, with an explicit manager-recovery message. A release owner must coordinate recovery of any such pending work before adopting the candidate. Refusal does not delete or rewrite the legacy row or unrelated drafts.

For an interrupted unbound Finish attempt whose temporary entry has expired, native checks the exact durable proof first. Original session/start/employee/location/drafts/queue stay saved. A fresh different observed identity is still refused by native before mutation; a fresh same identity repairs any preserved end time without changing it. An already captured exact old proof remains preferred, and no fresh scan or uncertain persistence error leaves the original attempt intact. Focused actual-handler and native-journal fixtures cover these boundaries.
