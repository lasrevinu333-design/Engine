## Behavior

`notification-presentation.js` serializes accepted presentation attempts and each episode's durable writer. Action/audio changes are staged in a snapshot only after earlier writes settle; an unconfirmed action cannot leak into a concurrent display/duplicate save. The protected mutation rechecks the exact action lease, including authority ABA. Concurrent lifecycle/poll calls coalesce without waiting indefinitely for an in-flight OS schedule call; stale card retirement is not held behind that call. Exact retirement remains retryable and reentrancy guarded.

The existing protected `bridge.js` save adapter now persists a positive safe-integer queue ordinal, its provenance, visual state and audio state alongside the exact principal/key/payload and displayed receipt flag. Allocation is inside the existing protected mutation. Confirmed save/readback precedes presentation and the first sound. Source order is local accepted-arrival order, not provider creation time or a clock claim. New rows use `accepted-local`; legacy rows use `legacy-recovered`. Legacy enumeration order cannot reconstruct original arrival order, and the marker explicitly preserves that limitation.

Display ownership is not a terminal employee action. A displayed browser row with `visualState=pending` returns on restart/pageshow, even if its one logical displayed receipt was already saved. Open/Dismiss/Acknowledge resolve the exact visual only after the existing action result and a durable local save. Dismiss remains local-only and does not create an acknowledged/delivered/business-completion receipt. Failed action persistence leaves the exact card retryable. Every asynchronous action rechecks current principal/authority and exact card; old actions cannot affect a successor.

The card remains plain text with existing in-app schedule routing and Open/Dismiss controls. Later queued cards do not overwrite an unresolved card. The next card waits for the previous card to resolve and its audio owner to finish. Hidden/detached renderer instances do not start cards; pagehide cancels only owned presentation/audio and pageshow creates a fresh action lease.

Before audio starts, the exact episode is durably `claimed`. Only two actual tone/speech completions produce `completed`. Failure is `incomplete`. A claimed, incomplete, completed or legacy-unknown episode is never silently replayed as a fresh two-cycle sequence. Legacy displayed rows are explicitly `legacy-unknown`, not falsely completed. This is at-most-one attempted episode, NOT a guarantee of two audible cycles across a crash: a crash between claim and sound, or in the middle, remains uncertain/incomplete and needs the accepted native audio/claim architecture to close the full obligation.

`memphis-device-reminders.js` now uses the selected inline waveform with exact HTML media `ended/error`, then the existing gap, then the exact WebView `SpeechSynthesisUtterance` object's `end/error`. The body is normalized once and identically spoken twice. No estimated speech duration, timer, or arbitrary 60-second wait is completion evidence. A missing callback leaves this owner pending rather than starting overlapping speech; visible Dismiss remains usable. Error/cancel does not claim successful completion. Pointer audio priming cannot replace a playing sequence. Debug-only legacy ringtone fallbacks remain separate from the guarded episode path.

Fully's documented `textToSpeech` returns no issuing-call token. Its broadcast queued/start/done IDs alone cannot prove correspondence to this request in the presence of another producer. This change therefore does not call that uncorrelated TTS path; it uses the exact WebView utterance route while preserving existing Fully kiosk/wake/volume ownership. No setting, update, license or OS policy is changed. Actual Android WebView speech support and an independently acceptable native/Fully completion-correlated adapter remain gates if this route is unavailable; silence is incomplete, not success. The current vendor API was inspected at [Fully's official integration documentation](https://www.fully-kiosk.com/en/#websiteintegration), not inferred from API names. No document claim substitutes for version-specific runtime proof.

## Design comparison requested by the parent — no activation

| Property | Accepted QP profile path | Online server-authorized / historical-notice alternative |
| --- | --- | --- |
| Authority at local effect time | Qualified native monotonic profile plus fresh authenticated raw-body nonce clock block bounds the entire request/observation interval; production owner validates validity window before effect | Server can authorize an operation at its own transaction time. Network receipt alone cannot prove that the client is still before expiry when displaying/playing it |
| Hardware numeric clock premise | Needs release-pinned target-specific deterministic error/rate/age bounds and evidence, not Android's generic monotonic wording | Can avoid that premise ONLY for an explicitly historical claim such as “server recorded this notice at …; current coverage unverified.” “Online checked just now” is not a deterministic freshness proof |
| Offline/pending semantics | Durable native claims/receipts and conservative local interval admission, original principal fenced | Durable original operation/receipt IDs can remain pending; retries are authenticated/idempotent; cached notices are dated historical information. Active responsibility/current overdue state is not asserted offline |
| Master obligations | Intended to satisfy current-before-expiry/assignment and complete offline/native delivery contracts without relabeling them | Would change or leave unmet NOT-008 and REV4.1-NOT-004/005/010..013 current-recipient/time-sensitive instructions, automatic lunch responsibility and overdue timing; it cannot silently count historical notices as current operational delivery |

The no-new-resource alternative can use the existing authenticated server and local protected queue in principle. It still requires a real mounted authorization API, SQL transaction/current-owner checks, exact operation/principal/assignment binding, nonce/raw-body response validation, replay/revocation/response-loss tests, explicit historical UI and speech wording, idempotent original receipt transport, trusted action reauthorization, and an independently reviewed native lifecycle/containment boundary. It does not authorize constructing new paid infrastructure, using HTTP Date/device wall time as authority, or treating provider acceptance as employee delivery.

Neither design eliminates the gap between server decision and delayed local effect. If the requirement remains “current and before expiry when speech/display occurs,” the historical alternative does NOT satisfy it. It may be a separately approved reduced-authority fallback, with truthful pending/offline state, but requires explicit requirement reconciliation and fresh architecture review before activation. This document makes no such choice and does not weaken QP-01 or enable the provider.
